# Инструкции для код-ревью

Файл для `/code-review` и похожих команд. Проект — статический сайт на GitHub Pages
(`index.html` — учитель, `cabinet.html` — родитель/ученик) + Firestore на бесплатном плане Spark.
Своего сервера нет: **правила `firestore.rules` — единственная защита данных**. Ревью идёт по
приоритетам ниже; находки из п. 1 и 2 — всегда блокирующие.

Как устроен доступ (сверяйся с комментарием в начале `firestore.rules`):

- `teacherSpaces/{uid}/…` — всё хозяйство учителя. Доступ только после входа (Firebase Auth,
  email + пароль) и только если `request.auth.uid == uid`. Старый вход по секретному ключу в пути
  (`teacherKey` / TEACHER_ID) **упразднён**; в коде остался только его одноразовый перенос и
  очистка `localStorage` (`LEGACY_KEY_STORAGE`).
- `parentAccess/{ключ}`, `studentAccess/{ключ}` — витрины кабинетов. Модель «ключ = пароль»:
  знаешь ключ — можешь прочитать ровно один документ, перечислить нельзя.
- `channels/{ключ канала}/items` — единственное место, куда пишут родитель и ученик (ДЗ, заявки,
  «оплачено», «пояснение», подписка на пуш). Только создание, состав полей ограничен `validItem`.

## 1. Главный приоритет — не утекли секреты и доступы разграничены строго

### 1.1. Ключи доступа и каналов нигде не «светятся»

Ключи `parentAccess`/`studentAccess` и ключи каналов — это пароли. Блокирующая находка, если
изменение:

- кладёт ключ туда, где его увидит кто-то ещё: в query-строку URL (только `#p=` / `#s=` во
  фрагменте — он не уходит на сервер), в заголовки, в `console.log`/`console.error`, в тексты
  ошибок, в аналитику, в `document.title`, в имена файлов, в данные для Cloudinary;
- публикует в витрину одного ученика что-то чужое: чужие `studentId`, названия занятий, id
  занятий, ключи или каналы. Чужие занятия попадают в витрину **только** как `busy: [{ s, e }]`
  без имён и id (`publishViews` / сборка `view` в `index.html`);
- отдаёт родителю/ученику учительские данные: заметки профиля, «материалы», ставки, `marks`,
  `pkgOverrides`, другие ключи. В витрину уходят только поля, перечисленные в сборке `view`;
- пишет ключ доступа в **общий** канал ученика (его читают и родитель, и ученик): там допустим
  только отпечаток `NotifyCore.pushKeyId(key)` (подписка на пуш). Так ключ родителя не узнает
  ученик и наоборот;
- ослабляет генерацию ключей: должен остаться криптостойкий генератор (`crypto.getRandomValues`),
  длина ≥ 24 символов (правила требуют `size() >= 24`);
- убирает `<meta name="referrer" content="no-referrer">` или `noindex, nofollow` в `cabinet.html`;
- ломает отзыв доступа: при отзыве ключа витрина удаляется, а каналы ученика ротируются (новый
  ключ канала). Подписки отозванного ключа в новый канал не копируются, старый канал очищается
  целиком. Фоновая рассылка не шлёт пуши на отозванные ключи (`keyMatches` +
  `active === false`).

### 1.2. `firestore.rules`

Любая правка правил — самое внимательное место ревью. Проверь:

- **Листинг выключен.** Для `parentAccess`, `studentAccess` разрешён только `get`, не `list`/`read`.
  Для `channels/{key}/items` `list` возможен только внутри канала, ключ которого известен.
  Итоговое `match /{document=**} { allow read, write: if false; }` остаётся последним и не
  ослаблено. Никаких collection-group правил.
- **Учитель = владелец.** Всё под `teacherSpaces/{uid}` разрешено только при `isTeacher(uid)`
  (`request.auth != null && request.auth.uid == uid`). Никаких `if true`, `if request.auth != null`
  без сравнения uid, никаких исключений «для удобства».
- **Запись от родителя/ученика — только через `validItem`:** `hasOnly([...])` с явным списком
  полей, `type` из фиксированного списка, лимиты длин, ссылки на файлы только
  `^https://res[.]cloudinary[.]com/`, `update: false` (менять чужие сообщения нельзя).
  Новое поле или тип — только с лимитом и тестом.
- **Витрины:** запись разрешена только с `validView` и ключом ≥ 24 символов; удаление — только
  по ключу. Если `validView` меняется — не должно стать возможным записать витрину без `v`/`role`
  или с огромными массивами.
- Каждое изменение правил сопровождается тестом в `tests/rules/` (эмулятор, `npm run test:rules`),
  в том числе **негативным**: чужой uid, листинг, лишнее поле, чужой домен файла.
- После слияния правил их нужно выкатить вручную (`firebase deploy --only firestore:rules`).
  Если PR меняет правила — в описании и в `DEVLOG.md` должно быть сказано, что нужен деплой.

### 1.3. Секреты в репозитории

Репозиторий **публичный**. Блокирующая находка — любой из:

- токены GitHub (`github_pat_…`, `ghp_…`, `gho_…`, `ghs_…`), ключи API, пароли, реальные email,
  uid учителя или ключи доступа в коде, тестах, фикстурах, `DEVLOG.md`, README;
- сервисный аккаунт Firebase (`private_key`, `BEGIN PRIVATE KEY`, `client_email` сервисного
  аккаунта). Он живёт **только** в секрете GitHub Actions `FIREBASE_SERVICE_ACCOUNT`;
- логи эмулятора и прочий мусор (`*.log` в `.gitignore` — не удалять оттуда).

Можно в коде (это публичные значения по замыслу Firebase/Cloudinary): `firebaseConfig`
(apiKey, projectId и т. п.), публичный VAPID-ключ пушей `FCM_VAPID_KEY`, имя облака Cloudinary
и имя **unsigned** preset. Защита держится на правилах, а не на их секретности.

## 2. Второй приоритет — архитектурные ограничения

Проект обязан оставаться бесплатным и без собственного сервера. Блокирующая находка, если
изменение добавляет:

- **Cloud Functions**, Firebase Hosting с серверной частью, Blaze-план или любой платный сервис;
- **VPS / свой бэкенд / serverless** (Vercel/Netlify functions, Workers и т. п.);
- **signed**-загрузку в Cloudinary или `api_secret` в коде. Файлы — только unsigned upload
  (`https://api.cloudinary.com/v1_1/<cloud>/auto/upload` с `upload_preset`);
- сборку/бандлер/npm-зависимости во фронтенде. Страницы — обычный HTML + JS-модули, библиотеки —
  с CDN (Firebase JS SDK с gstatic, FullCalendar с jsdelivr, html2canvas с cdnjs). Календари —
  только **FullCalendar**, без замены на другой календарь;
- новые способы входа или сторонний OAuth (Google OAuth был убран намеренно).

Разрешено и уже используется (не считать нарушением):

- **Firebase Authentication (email + пароль) — только для учителя.** Родители и ученики входят
  по ключу в ссылке, без аккаунтов;
- Firestore и Firebase Cloud Messaging на плане Spark;
- **фоновая рассылка пушей** `notifier/send.mjs` (firebase-admin) в GitHub Actions
  (`.github/workflows/notify.yml`, запуск по расписанию и внешним cron-job.org). Это единственный
  серверный код; он работает с сервисным аккаунтом из секрета. Правки здесь — с тестами
  `npm run test:notifier`. Логи Actions публичны, поэтому в `console.log` рассылки нельзя писать
  токены устройств, ключи доступа и тексты сообщений целиком;
- GitHub Pages для раздачи сайта, `sw.js` (service worker) для установки на экран «Домой» и пушей.

Также проверь:

- Старые данные не ломаются: названия занятий, отметки `marks` (по id занятия), `pkgOverrides`,
  ключи и каналы. Если меняется формат — нужен тихий однократный перенос с флагом в `state/main`
  (пример: `pkgByMarks`).
- Логика уведомлений одна для браузера и рассылки — `notify-core.js` без зависимостей. Не
  дублировать её в `index.html`/`cabinet.html`/`notifier/`.

## 3. Мобильная совместимость

Сайт в основном открывают **с телефона** (учитель — iPhone; родители — iPhone и Android), в том
числе как приложение с экрана «Домой». Проверь:

- ширина 360–430 px: ничего не вылезает по горизонтали, текст не наезжает (вкладки `.tabs .tab`
  не уже своей подписи — полоса прокручивается), кнопки не меньше ~44 px по высоте;
- у новых и изменённых полей ввода `font-size` ≥ 16 px, иначе iPhone приближает страницу при
  фокусе (у большинства старых полей пока 15 px — известный недочёт, не повод блокировать
  чужое изменение, но новое так делать не надо);
- нет опоры на hover, правый клик, двойной клик, клавиатурные сочетания как единственный способ
  действия (Ctrl+V для скриншотов — только дополнение к кнопке «+ добавить файл»);
- `viewport-fit=cover` и безопасные отступы сохранены; работают обе темы (светлая/тёмная, токены
  в `design.css`);
- `cabinet.html` **без** `manifest.json` намеренно: иначе иконка на экране «Домой» сохранит ссылку
  без ключа. Не добавлять manifest в кабинет и не стирать ключ из адресной строки;
- на iPhone веб-пуши работают только в приложении с экрана «Домой» (iOS 16.4+); тексты в кабинете
  должны это объяснять, а не молча ничего не делать;
- `window.open`, `alert`/`confirm` после `await`, автозапуск звука и т. п. Safari блокирует, если
  они вызваны не прямо в обработчике нажатия.

Тесты: `cd tests && npm run test:e2e` (есть профили iPhone/Android и замеры ширины
вкладок в `e2e/tabs.test.mjs`); скриншоты — `node tests/screens.mjs`.

### Известная проблема: экспорт PNG «Свободные окна» в Safari на iPhone

`exportScheduleImage()` в `index.html`. В Safari на iPhone не работают `window.open(...)`,
вызванный после `await html2canvas(...)` (он уже не «в нажатии» и блокируется), и
`<a download>` (Safari его игнорирует). Поэтому на iOS картинка показывается в модальном окне
(`showPngModal`): её сохраняют долгим нажатием или кнопкой «Поделиться» через
`navigator.share({ files })`. Это новое нажатие, и там Safari разрешает системное меню.
Ревью должно остановить изменения, которые:

- возвращают для iOS `window.open`/`<a download>` или делают любой из них после `await`;
- убирают ветку `isIOS` (включая iPadOS: `MacIntel` + `maxTouchPoints > 1`) или `showPngModal`;
- вызывают `navigator.share` не из обработчика нажатия (после `await` в том же обработчике —
  тоже риск: `toBlob` готовится заранее, при открытии окна);
- меняют шрифты или цвета клона таблицы без проверки в обеих темах.

Эмулятор Chromium этот баг не воспроизводит (WebKit в контейнере нет). При правках экспорта
проси у автора проверку на реальном iPhone.

## 4. Общие требования к изменению

- Тесты зелёные: `npm run test:e2e`, `npm run test:rules`, `npm run test:notifier`,
  `node tests/check-syntax.mjs index.html cabinet.html`. Не пропускать, не отключать и не
  ослаблять тесты ради зелёного прогона.
- `DEVLOG.md` дополнен записью об изменении (что, зачем, какие решения, что нужно сделать руками).
- Интерфейс и тексты — на русском, простыми словами (пользователь — не разработчик).
- Стиль кода как в окружающем коде: без сборки, комментарии на русском там, где логика неочевидна.
