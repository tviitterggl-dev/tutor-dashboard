# Инструкции для код-ревью

Файл для `/code-review` и похожих команд. Проект — статический сайт на GitHub Pages
(`index.html` — учитель, `cabinet.html` — родитель/ученик) + Firestore на бесплатном плане Spark.
Своего сервера нет: **правила `firestore.rules` — единственная защита данных**. Ревью идёт по
приоритетам ниже; находки из п. 1 и 2 — всегда блокирующие.

Как устроен доступ (сверяйся с комментарием в начале `firestore.rules`):

- `teacherSpaces/{uid}/…` — всё хозяйство учителя. Доступ только после входа (Firebase Auth,
  email + пароль) и только если `request.auth.uid == uid`. Старый вход по секретному ключу в пути
  (`teacherKey` / TEACHER_ID) **упразднён**; в коде остался только его одноразовый перенос и
  очистка `localStorage` (`LEGACY_KEY_STORAGE`).
- `parentAccess/{ключ}`, `studentAccess/{ключ}` — витрины кабинетов. Модель «ключ = пароль»:
  знаешь ключ — можешь прочитать ровно один документ, перечислить нельзя.
- `channels/{ключ канала}/items` — единственное место, куда пишут родитель и ученик (ДЗ, заявки,
  «оплачено», «пояснение», подписка на пуш). Только создание, состав полей ограничен `validItem`.

## 1. Главный приоритет — не утекли секреты и доступы разграничены строго

### 1.1. Ключи доступа и каналов нигде не «светятся»

Ключи `parentAccess`/`studentAccess` и ключи каналов — это пароли. Блокирующая находка, если
изменение:

- кладёт ключ туда, где его увидит кто-то ещё: в query-строку URL (только `#p=` / `#s=` во
  фрагменте — он не уходит на сервер), в заголовки, в `console.log`/`console.error`, в тексты
  ошибок, в аналитику, в `document.title`, в имена файлов, в данные для Cloudinary;
- публикует в витрину одного ученика что-то чужое: чужие `studentId`, названия занятий, id
  занятий, ключи или каналы. Чужие занятия попадают в витрину **только** как `busy: [{ s, e }]`
  без имён и id (`publishViews` / сборка `view` в `index.html`);
- отдаёт родителю/ученику учительские данные: заметки профиля, «материалы», ставки, `marks`,
  `pkgOverrides` (в т.ч. цену/скидку пакета `price`), другие ключи. В витрину уходят только
  поля, перечисленные в сборке `view`; у пакета — только `{ done, total, remaining }`;
- в групповом занятии отдаёт семье что-то о других участниках: в витрину уходит только своя копия
  занятия с `group: true` — без имён, `studentId`, id копий других участников, `groupId`/`groupOcc` и
  названия группы; своё групповое время не должно попадать в `busy`;
- использует `lessonId` из заявки `book` (семья просит новое занятие) как id документа
  занятия или вообще ищет по нему занятие: это только метка, придуманная кабинетом семьи.
  Занятие создаётся с id `bookLessonId(item)` = `"bk_" + id заявки` (подтверждение повторяемо:
  после сбоя или со второго устройства пишется тот же документ, копий нет; своё такое занятие
  `bookProblem` не считает помехой), ученик — из канала (`channelMeta`), а не из заявки;
  перед созданием — повторная проверка пересечений (`bookProblem`);
- пишет ключ доступа в **общий** канал ученика (его читают и родитель, и ученик): там допустим
  только отпечаток `NotifyCore.pushKeyId(key)` (подписка на пуш). Так ключ родителя не узнает
  ученик и наоборот;
- считает кнопку «Отменить заявку» в кабинете защитой данных. Она показывается только на своей
  ждущей заявке (`by` = роль открытого кабинета), но правило удаления в канале
  (`channelKey.size() >= 24`) не различает, кто удаляет: без входа у семьи через консоль браузера
  можно удалить и заявку второй стороны. Это граница модели «ключ = пароль», её не прятать.
  Учитель перед решением перечитывает заявку (`stillPending` в `teacher/requests.js`) и
  отозванную не применяет;
- доверяет полю `by` из сообщений каналов. Его пишет сам отправитель, а правила не отличают
  учителя от семьи. Кабинет учителя берёт ДЗ и пояснения из каналов только с `by` parent/student,
  «оплачено» — только с `by: "parent"`; `by: "teacher"` из канала никогда не применяется
  (`processChannel`, тест «подделка «от учителя»» в `family.test.mjs`). Раньше поддельное ДЗ
  «от учителя» уходило новым участникам группы — другой семье;
- ослабляет генерацию ключей: должен остаться криптостойкий генератор (`crypto.getRandomValues`),
  длина ≥ 24 символов (правила требуют `size() >= 24`);
- убирает `<meta name="referrer" content="no-referrer">` или `noindex, nofollow` в `cabinet.html`;
- ломает отзыв доступа: при отзыве ключа витрина удаляется, а каналы ученика ротируются (новый
  ключ канала). Подписки отозванного ключа в новый канал не копируются, старый канал очищается
  целиком. Фоновая рассылка не шлёт пуши на отозванные ключи (`keyMatches` +
  `active === false`);
- переносит ключ доступа из фрагмента (`#p=`/`#s=`) в `?…` адреса. В ссылках пушей в `?…` идёт
  только id занятия (`?lesson=`), ключ — по-прежнему во фрагменте: фрагмент не уходит на сервер
  и в заголовок Referer.

### 1.2. `firestore.rules`

Любая правка правил — самое внимательное место ревью. Проверь:

- **Листинг выключен.** Для `parentAccess`, `studentAccess` разрешён только `get`, не `list`/`read`.
  Для `channels/{key}/items` `list` возможен только внутри канала, ключ которого известен.
  Итоговое `match /{document=**} { allow read, write: if false; }` остаётся последним и не
  ослаблено. Никаких collection-group правил.
- **Учитель = владелец.** Всё под `teacherSpaces/{uid}` разрешено только при `isTeacher(uid)`
  (`request.auth != null && request.auth.uid == uid`). Никаких `if true`, `if request.auth != null`
  без сравнения uid, никаких исключений «для удобства».
- **Запись от родителя/ученика — только через `validItem`:** `hasOnly([...])` с явным списком
  полей, `type` из фиксированного списка, лимиты длин, ссылки на файлы только
  `^https://res[.]cloudinary[.]com/`, `update: false` (менять чужие сообщения нельзя).
  Новое поле или тип — только с лимитом и тестом.
- **Настройки кабинета (`accessPrefs`):** в `tabOrder` — только известные вкладки
  (`tabOrder.hasOnly([...])` = `CAB_TABS` в `cabinet/core.js`, сверяет `structure.test.mjs`).
  Новая вкладка кабинета — сначала в правила и деплой, потом в кабинет.
- **Доска и материалы** — разные поля профиля: `accessUrl` (одна ссылка, в витрине `boardUrl`) и
  `materials` (список). В витрину материалы идут только через `Materials.clean` (`materials.js`) —
  только ссылка и название, заметки учителя туда не попадают.
- **Материалы в витрине** (`materials`): не больше 10, у каждого только `url` (http/https, ≤ 500)
  и необязательный `title` (≤ 80). Циклов в правилах нет, поэтому элементы проверяются по номерам
  `[0]…[9]`. Поднимаешь лимит — добавь строки проверки, иначе лишние элементы пройдут без проверки.
- **Витрины:** запись разрешена только с `validView` и ключом ≥ 24 символов; удаление — только
  по ключу. Если `validView` меняется — не должно стать возможным записать витрину без `v`/`role`
  или с огромными массивами.
- Каждое изменение правил сопровождается тестом в `tests/rules/` (эмулятор, `npm run test:rules`),
  в том числе **негативным**: чужой uid, листинг, лишнее поле, чужой домен файла.
- Поддельная база e2e-тестов проверяет записи копией правил — `tests/stubs/rules-check.js`.
  Меняешь `firestore.rules` — меняй и её, и таблицу в `tests/rules/parity.test.mjs`: этот тест
  прогоняет одни и те же документы через эмулятор и через копию и падает, если они разошлись.
  Иначе e2e-тесты будут пропускать записи, которые настоящая база отклонит.
- После слияния правил их нужно выкатить вручную (`firebase deploy --only firestore:rules`).
  Если PR меняет правила — в описании и в `DEVLOG.md` должно быть сказано, что нужен деплой.

- кладёт токены устройств **учителя** (`state.teacherDevices`) куда-либо кроме её пространства
  `teacherSpaces/{uid}` (в каналы или витрины учеников);
- расширяет `cabinetViewCache` (последняя витрина на устройстве родителя/ученика) чем-то сверх
  самой витрины этого ключа или перестаёт стирать его в «Забыть кабинет».

### 1.3. Секреты в репозитории

Репозиторий **публичный**. Блокирующая находка — любой из:

- токены GitHub (`github_pat_…`, `ghp_…`, `gho_…`, `ghs_…`), ключи API, пароли, реальные email,
  uid учителя или ключи доступа в коде, тестах, фикстурах, `DEVLOG.md`, README;
- сервисный аккаунт Firebase (`private_key`, `BEGIN PRIVATE KEY`, `client_email` сервисного
  аккаунта). Он живёт **только** в секрете GitHub Actions `FIREBASE_SERVICE_ACCOUNT`;
- логи эмулятора и прочий мусор (`*.log` в `.gitignore` — не удалять оттуда).

Можно в коде (это публичные значения по замыслу Firebase/Cloudinary): `firebaseConfig`
(apiKey, projectId и т. п.), публичный VAPID-ключ пушей `FCM_VAPID_KEY`, имя облака Cloudinary
и имя **unsigned** preset. Защита держится на правилах, а не на их секретности.

## 2. Второй приоритет — архитектурные ограничения

Проект обязан оставаться бесплатным и без собственного сервера. Блокирующая находка, если
изменение добавляет:

- **Cloud Functions**, Firebase Hosting с серверной частью, Blaze-план или любой платный сервис;
- **VPS / свой бэкенд / serverless** (Vercel/Netlify functions, Workers и т. п.);
- **signed**-загрузку в Cloudinary или `api_secret` в коде. Файлы — только unsigned upload
  (`https://api.cloudinary.com/v1_1/<cloud>/auto/upload` с `upload_preset`);
- сборку/бандлер/npm-зависимости во фронтенде. Страницы — обычный HTML + JS-модули, библиотеки —
  с CDN (Firebase JS SDK с gstatic, FullCalendar с jsdelivr, html2canvas с cdnjs). Календари —
  только **FullCalendar**, без замены на другой календарь;
- новые способы входа или сторонний OAuth (Google OAuth был убран намеренно).
- Экономность чтений из Firestore. Был реальный инцидент: фоновая рассылка читала весь журнал уведомлений и все ключи доступа при каждом запуске (613 чтений за прогон), при частоте запуска раз в 5 минут это выливалось в ~176 000 чтений в сутки при лимите Spark-плана в 50 000 — рассылка переставала работать на весь день. Блокирующая находка, если изменение:читает целую коллекцию/документ там, где достаточно точечного запроса по известному ключу/id;добавляет чтение, которое масштабируется с историей проекта (растёт вместе с количеством накопленных записей), а не с объёмом реальной работы за один запуск;убирает или ослабляет существующую точечную фильтрацию (active == true, чтение только «живых» записей и т. п.) в пользу «прочитать всё и отфильтровать в коде».Для нового кода, который читает из базы чаще одного раза за пользовательское действие — прикинь, сколько чтений это даст при разумном сценарии использования (например, при частоте фоновых запусков или числе одновременных пользователей), и сравни с лимитом 50 000/сутки на весь проект.
- Кабинет учителя: второй инцидент (27.09) — каждое «Провёл»/правка перечитывали всю историю
  занятий дважды (пакеты и витрины семей), ~550 чтений на нажатие при 330 занятиях. Теперь
  `listLessons` и `listRequestDecisions` отвечаются из живых подписок (`liveWindow` в
  `teacherApi`: чтения — один раз при подписке, дальше только изменившиеся документы).
  Блокирующая находка — новый код, который на частое действие (отметка, правка, публикация
  витрин, открытие вкладки) делает `getDocs` по диапазону, растущему с историей, мимо этих
  подписок. Тест `tests/e2e/reads.test.mjs` считает чтения (`window.__fakeReads`).
  Диапазон шире окна подписки `listLessons` не читает целиком: из подписки — часть внутри окна,
  напрямую — только куски за краями (`rangeQuery` в `liveWindow`, помнятся до своей записи).
  Так аналитика за год и «все будущие занятия группы» не перечитывают всю историю.
  Запросы «все занятия ученика / серии» (`listLessonsOfStudent`, `listSeries`) растут с историей, поэтому допустимы только на редкое
  явное действие (переименовать, удалить, «это и следующие»), а не на открытие окна или вкладки.
  Так было с «ДЗ к следующему занятию»: 3 открытия окна давали ~1000 чтений.
  Вкладка «Уведомления» берёт счётчики пушей из самих уведомлений (`pushRuns`, `pushDelivered`,
  `pushLastAt` — их ведёт рассылка; старое — один раз перенесено в `pushLegacy`) и читает только
  «разово»/«перед занятием» и «сейчас» за 30 дней. Журнал `notifLog` целиком на открытие вкладки
  не читать. Рассылка пишет в уведомление только через `update` (не `set` с `merge`), иначе
  удалённое учителем уведомление воскресает пустым документом.

Разрешено и уже используется (не считать нарушением):

- **Firebase Authentication (email + пароль) — только для учителя.** Родители и ученики входят
  по ключу в ссылке, без аккаунтов;
- Firestore и Firebase Cloud Messaging на плане Spark;
- **фоновая рассылка пушей** `notifier/send.mjs` (firebase-admin) в GitHub Actions
  (`.github/workflows/notify.yml`, запуск по расписанию и внешним cron-job.org). Это единственный
  серверный код; он работает с сервисным аккаунтом из секрета. Правки здесь — с тестами
  `npm run test:notifier`. Логи Actions публичны, поэтому в `console.log` рассылки нельзя писать
  токены устройств, ключи доступа и тексты сообщений целиком;
- GitHub Pages для раздачи сайта, `sw.js` (service worker) для установки на экран «Домой» и пушей.

Также проверь:

- Старые данные не ломаются: названия занятий, отметки `marks` (по id занятия), `pkgOverrides`,
  ключи и каналы. Если меняется формат — нужен тихий однократный перенос с флагом в `state/main`
  (пример: `pkgByMarks`).
- Логика уведомлений одна для браузера и рассылки — `notify-core.js` без зависимостей. Не
  дублировать её в `index.html`/`cabinet.html`/`notifier/`.

### Как устроен код кабинетов

Код кабинета учителя лежит не в `index.html`, а в файлах `teacher/*.js`. Это обычные скрипты
без `type="module"` и без обёртки `(function () { … })()`, подключённые `<script src>`
по порядку. `teacher/main.js` идёт последним: в нём запуск и оставшиеся обработчики. Все файлы
делят одно общее пространство имён, как если бы это был один большой скрипт. Firebase-обвязка
(`window.TutorFB`, `window.TutorAuth`) остаётся модулем в самом `index.html`. Проверь:

- **Новый файл** подключён в `index.html` перед `teacher/main.js` и добавлен в `SHELL` в `sw.js`
  в том же порядке. Иначе без сети кабинет не откроется. Изменился любой файл из `SHELL` —
  подними версию `CACHE`. Проверяет `tests/e2e/structure.test.mjs`.
- **Имена не повторяются между файлами.** Повтор `let`/`const` ломает страницу при загрузке,
  а повтор `function` молча подменяет одну функцию другой. Проверяет тот же тест.
- **Порядок загрузки.** Код, который выполняется сразу при загрузке файла, может использовать
  только то, что объявлено в этом же или в более раннем файле. Это вызовы функций и
  `addEventListener(…, имяФункции)` без стрелки. Функции «всплывают» только внутри своего файла.
  Внутри обработчиков и функций, которые вызываются позже, можно обращаться к чему угодно.
- **Кабинет семьи** устроен так же: код — `cabinet/*.js`, `cabinet/main.js` последним. Отличия:
  Firebase подключает модуль в самом `cabinet.html` и кладёт базу и нужные функции SDK в
  `window.CabFB`. Файлы `cabinet/*.js` подключаются с `defer`: так они выполняются по порядку
  **после** модуля. Первая строка каждого — `"use strict";`: код раньше был модулем, а модуль
  всегда строгий. Нужна новая функция SDK — добавь её в `window.CabFB` и в разбор в первом файле.
- **Имена не совпадают со встроенными именами окна.** В обычном скрипте `function open()`
  подменила бы `window.open` для всей страницы; в модуле такой проблемы не было, поэтому при
  переносе `open` стала `openCabinet`. Список опасных имён — в `structure.test.mjs`.

## 3. Мобильная совместимость

Сайт в основном открывают **с телефона** (учитель — iPhone; родители — iPhone и Android), в том
числе как приложение с экрана «Домой». Проверь:

- ширина 360–430 px: ничего не вылезает по горизонтали, текст не наезжает (вкладки `.tabs .tab`
  не уже своей подписи — полоса прокручивается), кнопки не меньше ~44 px по высоте;
- у новых и изменённых полей ввода `font-size` ≥ 16 px, иначе iPhone приближает страницу при
  фокусе (у большинства старых полей пока 15 px — известный недочёт, не повод блокировать
  чужое изменение, но новое так делать не надо);
- нет опоры на hover, правый клик, двойной клик, клавиатурные сочетания как единственный способ
  действия (Ctrl+V для скриншотов — только дополнение к кнопке «+ добавить файл»);
- `viewport-fit=cover` и безопасные отступы сохранены; работают обе темы (светлая/тёмная, токены
  в `design.css`);
- `cabinet.html` **без** `manifest.json` намеренно: иначе иконка на экране «Домой» сохранит ссылку
  без ключа. Не добавлять manifest в кабинет и не стирать ключ из адресной строки;
- на iPhone веб-пуши работают только в приложении с экрана «Домой» (iOS 16.4+); тексты в кабинете
  должны это объяснять, а не молча ничего не делать;
- поля ввода на телефоне — не меньше 16px, иначе Safari увеличивает страницу при нажатии. Общее
  правило в `design.css` (`@media (hover: none) and (pointer: coarse)`); проверяет
  `e2e/mobile-inputs.test.mjs`. Новое поле в новом окне добавь в этот тест;
- нажатие на пуш (`notificationclick` в `sw.js`) ищет уже открытую вкладку по адресу **без**
  `?lesson=…` (`tabKey`: у кабинета семьи — вместе с `#p=`/`#s=`, у учителя — без `#…`) и шлёт ей
  `postMessage({ type: "open-lesson", lessonId })`; новую вкладку открывает, только если своей
  нет. Сравнение адреса целиком (как было) открывало бы новую вкладку на каждый пуш. Страница
  открывает карточку, только когда данные загружены; занятия нет — никаких alert/ошибок.
  Проверяют `tests/notifier/sw.test.mjs` и `tests/e2e/push-open.test.mjs`;
- у каждого окна (модалки) есть × в правом верхнем углу — его добавляет общая `openModal()`
  (обе страницы, стиль `.modal-x` в `design.css`). Свой × в шаблон окна не вставлять; первым
  элементом окна должен быть `<h2>` (у него место под ×);
- `window.open`, `alert`/`confirm` после `await`, автозапуск звука и т. п. Safari блокирует, если
  они вызваны не прямо в обработчике нажатия.

- **Офлайн:** любая новая запись в базу обязана без сети сразу отказывать с понятным текстом:
  у учителя — через `guardWrites` (методы `set/patch/save/update/delete/publish/add…` в
  `TutorFB`) и `offlineToast`; в кабинете — через `requireOnline()` / `addItem`. Нельзя
  оптимистично менять экран до проверки сети. Новые библиотеки с CDN — в список `CDN` в `sw.js`
  (и поднять версию `CACHE`).

Тесты: `cd tests && npm run test:e2e` (есть профили iPhone/Android и замеры ширины
вкладок в `e2e/tabs.test.mjs`); скриншоты — `node tests/screens.mjs`.

### Известная проблема: экспорт PNG «Свободные окна» в Safari на iPhone

`exportScheduleImage()` в `index.html`. В Safari на iPhone не работают `window.open(...)`,
вызванный после `await html2canvas(...)` (он уже не «в нажатии» и блокируется), и
`<a download>` (Safari его игнорирует). Поэтому на iOS картинка показывается в модальном окне
(`showPngModal`): её сохраняют долгим нажатием или кнопкой «Поделиться» через
`navigator.share({ files })`. Это новое нажатие, и там Safari разрешает системное меню.
Ревью должно остановить изменения, которые:

- возвращают для iOS `window.open`/`<a download>` или делают любой из них после `await`;
- убирают ветку `isIOS` (включая iPadOS: `MacIntel` + `maxTouchPoints > 1`) или `showPngModal`;
- вызывают `navigator.share` не из обработчика нажатия (после `await` в том же обработчике —
  тоже риск: `toBlob` готовится заранее, при открытии окна);
- меняют шрифты или цвета клона таблицы без проверки в обеих темах.

Эмулятор Chromium этот баг не воспроизводит (WebKit в контейнере нет). При правках экспорта
проси у автора проверку на реальном iPhone.

## 4. Общие требования к изменению

- Тесты зелёные: `npm run test:e2e`, `npm run test:rules`, `npm run test:notifier`,
  `node tests/check-syntax.mjs index.html cabinet.html`. Не пропускать, не отключать и не
  ослаблять тесты ради зелёного прогона.
- Стенд e2e роняет тест, если на любой его странице была ошибка JS или `console.error`. Тест, который
  нарочно ломает сеть или базу, пишет `app.expectErrors = /…/` с конкретным текстом, а не
  общим «что угодно».
- `DEVLOG.md` дополнен записью об изменении (что, зачем, какие решения, что нужно сделать руками).
- Интерфейс и тексты — на русском, простыми словами (пользователь — не разработчик).
- Стиль кода как в окружающем коде: без сборки, комментарии на русском там, где логика неочевидна.
- Групповые занятия — копии занятия у каждого участника (`groupId` + `groupOcc`). Код, который
  считает занятия «штуками» или часами (календарь, «Итоги», «Аналитика»), должен склеивать копии
  одного `groupOcc`; деньги, «Провёл», пакет, «Оплачено» — по каждой копии. Групповые правки
  (время, перенос, отмена, отчёт, ДЗ) идут через групповые функции и не переписывают названия
  копий; «это и следующие» у обычного занятия не должно задевать копии других учеников.
- Окно группового занятия (`groups.js`) и обычное окно (`lesson-modal.js`) пользуются общими
  функциями: `modalBusy` (кнопка в окне, `core.js`), `publishReport` и `saveCallLink`
  (`lesson-ops.js`), `uploadFilesChecked` и `exportIcs` (`files.js`). Правку поведения
  вносить туда, а не копией в одно из окон: копии уже разъезжались (запись 42 в DEVLOG).
